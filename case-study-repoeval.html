Case study / AI evaluation

RepoEval Lab

A small Python harness for repository-style coding tasks. The core question: can an external behavioral verifier distinguish a correct implementation from a plausible but broken one?

Python · pytestAI-assisted learning projectPublished on GitHub

01 / The problem

A green exit code is not enough.

A coding-task evaluation needs a clear contract, tests separate from the candidate solution, and a report that tells an evaluator what actually ran. A verifier that silently accepts an all-skipped suite can produce a misleading pass, while inherited local pytest options can change results between machines.

  • Manifest paths are resolved and checked to stay inside the task directory.
  • All-skipped tests cannot count as a passing submission.
  • Timeouts retain any captured output and record elapsed wall-clock time.
  • Third-party pytest auto-loading and inherited pytest option overrides are disabled for task runs.

04 / Decisions and limits

Useful evaluation is not secure execution.

The runner launches candidate code in a subprocess so a time limit and result capture are possible. It does not provide a security sandbox: a timeout is not a filesystem, network, or resource boundary. Only trusted submissions should run on an ordinary host; untrusted tasks need properly isolated execution infrastructure.

The current runner is Python/pytest-specific. These example tests establish behavior for the tested cases, not general correctness or model capability. Mutation scoring, container isolation, broader task coverage, and richer resource metrics remain open work.
